# QQ NT（Windows 9.9.x）导出：现状与技术笔记

> 目标：像微信那样导出「和某个好友 / 某个群」的全部聊天记录。
> 当前状态：**库结构、参数探测、逐页解密已完成并自检通过；缺的是口令和消息字段映射。**

## 1. 已经确认的事实（本机实测）

| 项目 | 结论 | 依据 |
|---|---|---|
| 文件布局 | **1024 字节自定义头 + N × 4096 页** | `(文件大小 - 1024) % 4096 == 0`，22 个库全部成立 |
| 伪装的头部 | 头里写的是 `SQLite header 3`（真头是 `SQLite format 3\0`） | 前 16 字节对比 |
| 加密算法 | SQLCipher，AES-256-CBC | 公开资料 + 解密回环验证 |
| KDF 迭代 | **4000**（不是 SQLCipher 默认的 256000） | 多个已跑通的项目一致 |
| HMAC 算法 | **资料互相矛盾**：有说 HMAC-SHA1、有说 HMAC-SHA512 | 所以代码里不写死，见第 3 节 |
| 密钥 | 16 位 ASCII passphrase | 公开资料 |
| 密钥可见性 | **不常驻内存**：本机扫了 900MB（7 个 QQ 进程）也没找到 | 实测 |

最后一条是关键：QQ 的 passphrase 只在 `nt_sqlite3_key_v2` 被调用的**那一瞬间**存在于寄存器里。
社区工具（`QQBackup/qq-win-db-key`）的做法是：静态分析 `wrapper.node` 找到该函数 →
用调试器拉起 QQ 下断点 → 在用户重新登录时读取寄存器。

## 2. 为什么本项目不内置取密钥

那套做法需要「以调试器启动 QQ + 让用户重新登录」，属于对目标进程的调试介入，
和本项目「只读、不注入、不 hook」的原则冲突，也会打扰用户（要退出正在用的 QQ）。
所以本项目的定位是：**口令由用户提供一次，之后可复用**。

取口令的两条路（自己选）：

1. 用社区工具取一次（自行阅读其代码后再运行），拿到那 16 位字符串；
2. 如果你的 QQ 版本导出了 `sqlite3_key` 符号，也可以自己用 WinDbg / x64dbg 下断点抓。

拿到后建议放环境变量，避免留在命令历史里：

```powershell
$env:QQ_DB_KEY = "xxxxxxxxxxxxxxxx"
```

## 3. 参数自动探测

不同 QQ 版本可能用不同组合，所以 `wxexport/qq.py` 里列了一组候选参数，
逐个拿 page1 的 HMAC 去试，试通的那个才拿来解密：

| 名称 | 迭代 | KDF | HMAC | 保留区 |
|---|---|---|---|---|
| `qq/sha1-48` | 4000 | SHA512 | SHA1 | 48 |
| `qq/sha1-36` | 4000 | SHA512 | SHA1 | 36 |
| `qq/sha512-80` | 4000 | SHA512 | SHA512 | 80 |
| `qq/legacy-sha1` | 4000 | SHA1 | SHA1 | 48 |
| `qq/iter64000` | 64000 | SHA512 | SHA1 | 48 |
| `sqlcipher-default` | 256000 | SHA512 | SHA512 | 80 |

页面布局（以保留区 48 为例）：

```
page1 : [salt 16][密文 4032][IV 16][填充 12][HMAC-SHA1 20]
其它页: [密文 4048][IV 16][填充 12][HMAC-SHA1 20]
```

注意 **HMAC 永远在页尾**，填充在它前面——这一点和直觉相反，自检里专门造了数据验证。

## 4. 现在能用的命令

```bash
python qq_export.py probe                     # 找库 + 检查结构（不需要口令）
python qq_export.py decrypt --key <16位口令>   # 逐库解密到 work/qq_decrypted/
python qq_export.py schema                    # 打印解密后的表与列
```

`decrypt` 会自己试参数，命中后打印用的是哪一套；解完跑 `PRAGMA integrity_check`，
不通过会标 `WARN`（不静默失败）。

## 5. 还差什么（下一步）

1. **一次真实解密**（缺的就是口令）。跑通后 `schema` 会打印出 `c2c_msg_table` /
   `group_msg_table` 的真实列名，才能确定字段映射。
2. **消息体解析**：QQ NT 的正文是 protobuf（`MsgBody → repeated MsgContent`），
   要按真实样本校准元素类型（文本 / 图片 / 文件 / 卡片）。
3. **媒体定位**：QQ 的图片和文件在 `nt_data/` 下，命名与消息里的 md5 对应关系要摸清。
4. **复用渲染**：entries 对齐后直接走现有 `exporter`，HTML / TXT / CSV 不用重写。

## 6. 已知差异（和微信比）

| 维度 | 微信 | QQ NT |
|---|---|---|
| 自定义头 | 无 | 1024 字节 |
| KDF 迭代 | 由 WCDB 决定 | 4000（远低于默认） |
| 密钥形态 | 32 字节二进制 | 16 位 ASCII |
| 密钥获取 | 只读内存即可 | 需要调试器，或用户提供 |
| 消息正文 | XML / JSON / 纯文本 | protobuf |
