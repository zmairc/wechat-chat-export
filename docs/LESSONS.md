# 微信导出原型：踩过的坑与可复用结论

> 这份文档是「做下一个平台之前先读一遍」的清单。
> 每条都标了 **适用范围**：`通用`（换平台也要遵守）、`微信专属`（可以在新平台换写法）、
> `必须重做`（每个平台都不一样，照抄必错）。
>
> 场景：把本项目的引擎（`wxexport/`）当作原型，扩展到 QQ / 飞书 / 钉钉 / 抖音，
> 最终做成能在手机上选「哪个 App、跟谁」直接导出的产品。

---

## A. 边界与合规（通用，不能松）

| # | 注意点 | 为什么 |
|---|---|---|
| A1 | **只读原始数据**，绝不写回、不改库、不删缓存 | 用户信任的底线；写回会触发 App 自己的校验，甚至损坏数据 |
| A2 | **不注入、不 hook 进程**，只做 `ReadProcessMemory` 只读访问 | 注入是各家风控的重点打击面（钉钉明确列为禁止项），换成读内存风险低一个量级 |
| A3 | **不联网**：没有上传通道，产物只落本地 | 是卖点也是免责的前提；一旦有网络行为，性质就变了 |
| A4 | **密钥不落明文**、日志不打印密钥 | 本项目用 DPAPI 加密缓存；换平台必须保留这个策略 |
| A5 | 只处理**你本人本机已登录**的账号，README/首屏必须写清 | 避免被当成取证工具 |
| A6 | 明确写「不保证长期可用」，App 一升级格式就变 | 减少用户预期落差，也给自己留余地 |
| A7 | 企业场景（飞书/钉钉）走**官方 API + 管理员授权**，不走本地破解 | 合规成本最低、可用性最高，见 `ROADMAP.md` |

## B. 三条取数路线（先选路线，再写代码）

| 路线 | 适用 | 优点 | 代价 |
|---|---|---|---|
| **① 官方 API** | 飞书（`im/v1/messages`）、钉钉（仅企业版「消息同步」）、企业微信 | 稳定、合法、字段清晰 | 要建应用、要授权、有频率限制、拿不到本人以外的历史 |
| **② 本地数据库解密** | 微信桌面端、QQ NT 桌面端 | 全量、离线、字段最全 | 需要从内存/文件取密钥，格式随版本变 |
| **③ 系统备份解析** | iOS 备份（iTunes/Finder）、部分 Android 厂商备份 | **手机上唯一不需要 root/越狱的路** | 需要用户先备份，体积大，加密备份要密码 |

**关键判断**：手机上装一个 App 直接读别的 App 的沙盒，在 iOS 上不可能（沙盒隔离），
在 Android 上要 root。所以「手机 App」的形态只能是 **③ 备份解析 + 查看器**，
或「手机只当遥控器、真正解密在 PC」。详见 `ROADMAP.md` 第 3 节。

## C. 加密数据库：SQLCipher 参数千万别假设（必须重做）

微信的参数和 SQLCipher 官方默认值**不一样**，QQ NT 的又和微信不一样。
下表是实测值，做新平台时**必须先用一个样本验证，不能照抄**：

| 项目 | 微信 4.x（实测） | QQ NT 9.9.x（公开资料） | SQLCipher 默认 |
|---|---|---|---|
| 页大小 | 4096 | 4096 | 4096 |
| 保留字节 | 80（16 IV + 64 HMAC） | 未公开，需实测 | 0/16/48/80 视版本 |
| KDF 迭代 | 由 WCDB 决定（抓样本反推） | **4000**（≠ 默认 256000） | 256000 |
| HMAC 算法 | HMAC-SHA512 | **资料互相矛盾**：有说 SHA1、有说 SHA512，必须实测 | SHA512 |
| 自定义头 | 无（page1 前 16 字节是 salt） | **前置 1024 字节自定义头，必须先剥掉** | 无 |
| 密钥形态 | 32 字节二进制（hex 64 位） | **16 字节 ASCII 字符串** | 任意 |

**教训**：
- 别相信"SQLCipher 4 就是那套参数"，各家都会改 KDF 迭代甚至 HMAC 算法；
- **验证密钥的唯一标准是 page1 的 HMAC**，算不对就换参数重试，不要"解出来看着像"就用；
- 有自定义头的，剥离长度要靠**文件长度整除页大小**来反推（微信 `.dat` 也是这个思路）；
- WAL 不要无条件回放：先只解主库跑 `PRAGMA integrity_check`，不过再试回放，否则会把已 checkpoint 的帧重复写入。

## D. 取密钥（微信专属思路，可复用"先验证再缓存"）

| # | 注意点 |
|---|---|
| D1 | 微信 4.1+ 内存里不再有明文 hex，要顺着 `com.Tencent.WCDB.Config.Cipher` 对象解密混淆 blob；换平台时这段**必须重写**，但"特征串 → 引用 → 对象 → 去混淆 → 正则"的套路可以复用 |
| D2 | **密钥必须过 page1 HMAC 校验**才允许使用；校验不过就当没找到，绝不能带着猜测的密钥去解密 |
| D3 | 同一账号的多个库可能共用一把 key（QQ 是同一个库文件），也可能各自独立——按"逐库缓存 + 逐库校验"最稳 |
| D4 | 取完就缓存，用户第二次导出不必开 App；缓存**必须加密**（Windows DPAPI / macOS Keychain / iOS Keychain） |
| D5 | 进程会改名：微信从 `WeChat.exe` 变成 `Weixin.exe`；写死进程名迟早失效，要按"窗口类名/特征模块/内存特征"识别 |
| D6 | 密钥会随重新登录变化，缓存要能失效重取（本项目用 HMAC 校验兜底，等价于自动失效） |

## E. 媒体文件（微信专属格式，但"三段结构"很常见）

| # | 注意点 |
|---|---|
| E1 | 微信图片 `.dat` = `15B 头 + AES 段 + 明文段 + XOR 段`，`15 + align16(aes_size) + xor_size == 文件长度` 可用来校验理解是否正确 |
| E2 | **V2 的两把密钥都能从账号级 uin 派生**：`aes = md5(uin+wxid)[:16]`、`xor = uin & 0xFF`；uin 从 MMKV 文件名读。别去扫全内存（慢且不可靠） |
| E3 | 验证密钥必须**同时看头尾**：只看文件头魔数会把"头部正常、尾部花屏"的坏图当成成功 |
| E4 | 约六成"图片"其实是 HEVC（`wxgf` 容器），要抽 Annex-B 流；容器头部可能有**假 VPS**，要挑 `layer_id=0` 的那个 |
| E5 | 每张原图旁边都有 `_t` 缩略图（普通 JPEG）——没有解码器时用它兜底，体验比"打不开的文件"好得多 |
| E6 | **解码器（ffmpeg）只能是可选依赖**：有就转，没有就抽流+缩略图，绝不因此失败 |
| E7 | 媒体搬不动/解不开时**保留原文件并显式标注**，永远不要静默丢弃 |

## F. 消息模型（微信专属 schema，但四个坑通用）

| # | 注意点 | 通用性 |
|---|---|---|
| F1 | 会话数据会**分片**（`message_0.db` / `message_1.db`），必须按会话合并 | 通用 |
| F2 | 发送者映射（`Name2Id`）**逐库不同**，同一个 id 在不同库里可能指向不同人，禁止硬编码 1=我 | 通用 |
| F3 | 类型字段常带"高位标记 + 低 32 位类型"，不要整型直接比较 | 通用 |
| F4 | 正文可能是压缩的（zstd，魔数 `28 b5 2f fd`）；没有解压器时先把原文留着 | 通用 |
| F5 | 卡片类消息（链接/转账/小程序/文件）正文是 XML/JSON，解析要**容错**，解析失败就展示原文 | 通用 |
| F6 | **未知类型不要丢**：保留 `type + 原始 hex/文本`，后续补解析时还能救回来 | 通用 |

## G. 渲染与导出（基本可整段复用）

| # | 注意点 |
|---|---|
| G1 | HTML 用**相对路径**引用 `media/`，整个目录拷走就能看；不要内联 base64（几千张图会炸内存） |
| G2 | 消息量大时用**流式写文件**，别先拼一个大字符串（本项目的做法已验证 5000+ 条） |
| G3 | CSV 要 **UTF-8 with BOM**，否则 Excel 打开是乱码；引号/换行交给 `csv` 模块 |
| G4 | 页面要能搜索、能"只看带图"，还要能**打印成 PDF**（很多人的真实用途就是这个） |
| G5 | 时间戳单位各家不同（秒/毫秒/微秒），统一在适配层转成秒 |

## H. 工程实践（通用，都是血泪）

| # | 注意点 |
|---|---|
| H1 | **零第三方依赖**是个强约束也是卖点：加密走系统 API（CNG/DPAPI/Keychain），压缩自己兜底 |
| H2 | Windows 控制台默认 cp1252，print 中文会崩；启动时 `stdout.reconfigure(encoding="utf-8")`，CI 里设 `PYTHONUTF8=1` |
| H3 | `.bat` 仓库里存 LF，靠 `.gitattributes` 检出成 CRLF，否则下载后双击报错 |
| H4 | **自检要造数据**：自己加密再解开，不读真实数据也能在 CI 跑（本项目 9 组断言） |
| H5 | **断言必须带消息**。我们踩过：裸 `assert` 抛的 `AssertionError` 消息为空，CI 日志只剩 `[FAIL] check_dat_formats: `，白查两小时 |
| H6 | 失败路径永远比成功路径重要：每个 `except` 都要决定"是降级、是保留原文件、还是明确报错" |
| H7 | 输出目录、缓存目录默认放**用户目录**，别写在程序目录（Program Files 没写权限） |

## I. 换平台检查清单（照这个顺序做，别跳步）

1. **摸数据在哪**：`%APPDATA%` / `%LOCALAPPDATA%` / 安装目录 / `Documents`，找"最近被写过"的目录
2. **判断是否加密**：读文件头 16 字节，是 `SQLite format 3\0` 就直接开；是随机字节就是加密
3. **量清楚加密参数**：页大小、保留字节、KDF 迭代、HMAC 算法、有无自定义头、密钥长度
4. **解决密钥来源**：内存 / 配置文件 / 系统凭据 / DPAPI / 官方授权
5. **先打通文本**：一个会话 → 全量消息 → TXT。**不要一上来做媒体**
6. **再上 HTML/CSV**：复用现有 `exporter`，只把 entries 结构对齐
7. **最后做附件**：先摸清命名与加密，做不出来就保留原文件并标注
8. **补自检 + CI**：照 `selftest.py` 的套路，自造密文再解开
9. **写清楚能力边界**：哪些拿不到、为什么拿不到，写在 README 最显眼处

## 附：一句话版的"别踩"

> 别假设加密参数；别用没验证过的密钥；别只看文件头；别丢未知消息；
> 别静默失败；别让解码器成为硬依赖；更别 hook 别人的进程。
