# 多平台 + 移动端：路线图

> 目标：把当前「微信桌面端导出」的引擎抽象成可插拔的适配层，逐步支持 QQ / 飞书 / 钉钉 / 抖音，
> 最终做成能在手机上选「哪个 App、跟谁」就导出的产品。
>
> 配套文档：`ARCHITECTURE.md`（现有架构）、`LESSONS.md`（所有踩过的坑）、`REFERENCES.md`（同类项目）。

---

## 1. 先泼一盆冷水：三条硬约束

这三条决定了产品形态，绕不过去：

**① 手机上装个 App 直接读别人 App 的聊天库，做不到。**
iOS 每个 App 是独立沙盒，非越狱设备上没有任何合法途径读微信/QQ 的 `Documents`；
Android 上要 root（或用厂商的"手机搬家"备份）。

**② 应用商店基本不会收。**
App Store 审核指南 5.1.1/5.1.2 明确限制"读取其他 App 的数据"，这类工具大概率被拒；
Google Play 对"访问其他应用私有数据"同样严格。现实的分发方式是：
桌面端为主 + 移动端走 TestFlight / 自签 / 企业内部分发。

**③ 官方 API 是唯一"长期可用"的路线，但它只覆盖企业 IM。**
飞书有 `im/v1/messages`；钉钉只对企业版开放「消息同步」且审核极严；
微信/QQ/抖音**没有**面向个人的聊天记录导出 API。

所以真实可行的产品是：**「本地备份解析器 + 查看器」**，
而不是「一个 App 通吃所有聊天软件」。这一点最好在立项时就写进产品文案。

## 2. 平台可行性矩阵

| 平台 | 取数路线 | 数据/密钥位置 | 难度 | 风险 | 优先级 |
|---|---|---|---|---|---|
| **微信 桌面端** | 本地库解密 | `xwechat_files\<wxid>\db_storage`；密钥在进程内存 `Config.Cipher` | 已完成 | 中（版本变更） | ✅ 基线 |
| **QQ NT 桌面端** | 本地库解密 | `nt_db/nt_msg.db`，**前置 1024 字节自定义头**；密钥是 16 字节 ASCII，从进程内存取 | 中 | 中 | **P0** |
| **飞书** | **官方 API** | `im/v1/messages`，需自建应用 + 机器人在群内 + 用户授权 | 低 | 低（合规） | **P1** |
| **钉钉** | 仅企业 API | 「消息同步」只对认证企业开放，需服务端回调，明确禁止客户端逆向 | 高 | **高（协议禁止）** | P3（不承诺） |
| **抖音** | **只做链接卡片** | 无桌面端、无个人导出 API，本地库加密且随版本变 | 高 | 高 | P2（降级方案） |
| **微信 iOS** | 系统备份解析 | Finder/iTunes 备份里的 `AppDomain-com.tencent.xin/Documents` | 中 | 低 | **P2** |
| **微信/QQ Android** | root 或厂商备份 | `/data/data/<pkg>/`，需 root | 高 | 高 | P4 |

**抖音这条要特别说明**：你说的"分享视频显示连接"其实是**链接渲染**问题，不是取数问题——
在已经能导出的会话里，把 `v.douyin.com/xxx` 这类短链识别成卡片（标题 + 封面 + 可点开）即可。
要不要联网取标题，做成显式开关（默认关，保持"不联网"承诺）。

## 3. 架构：把「平台差异」关进适配层

现有 `wxexport/` 的分层已经是对的（取密钥 → 解密 → 读消息 → 渲染），
只差把「微信专属」的那几块抽出来变成接口：

```
             ┌──────────────────────────────────────────┐
             │  core/   （跨平台复用，几乎不用改）        │
             │  exporter(html/txt/csv) · schema · cli   │
             └───────────────▲──────────────────────────┘
                             │ Conversation / Message / Attachment
             ┌───────────────┴──────────────────────────┐
             │  platforms/<app>/  （每个平台一个目录）    │
             │  locate()  找数据目录                     │
             │  keys()    取密钥（内存/API/备份）         │
             │  decrypt() 解密数据库（SQLCipher 参数各异）│
             │  store()   会话与消息读取                  │
             │  parse()   类型/卡片 → 可读文本            │
             │  media()   图片/视频/文件落盘              │
             └──────────────────────────────────────────┘
```

统一数据契约（**先定这个，后面所有平台都往里填**）：

```python
@dataclass
class Message:
    ts: int                 # 秒
    sender_id: str
    sender_name: str
    is_self: bool
    kind: str               # text/image/voice/video/file/link/card/system/...
    text: str               # 给人看的文本（一定非空，最差也要是 [未知类型 0x1234]）
    quote: str = ""
    attachments: list = ()  # {path, name, size, mime, thumb}
    raw_type: int = 0       # 原始类型，保留以便以后补解析
```

适配器接口（**每个平台必须实现全部方法，缺能力就返回 None 并在 UI 上说明**）：

```python
class Platform:
    name: str
    def available(self) -> bool: ...
    def locate(self) -> list[Account]: ...
    def keys(self, account) -> dict: ...
    def open_store(self, account) -> Store: ...   # chat_index / messages
    def parse(self, raw_msg) -> Message: ...
    def media(self, msg, out_dir) -> list[Attachment]: ...
```

**验收标准**：加一个平台不需要改 `exporter.py` 一行代码。

## 4. 移动端：三种形态，选一种

| 形态 | 怎么做 | 体验 | 现实性 |
|---|---|---|---|
| **A. 纯本地 App**（Android） | 导入 root 备份或厂商备份 → 本地解密 → 生成 HTML | 一步到位 | Android 可行但门槛高（root）；iOS 只能靠备份文件，需用户先连电脑备份 |
| **B. 手机 + PC 引擎** | 手机通过局域网/数据线让 PC 跑引擎，手机只浏览 | 体验最好 | 要写 PC 服务端；违背"不联网"承诺（需明示为局域网） |
| **C. 手机只做查看器** | PC 导出 zip → 手机导入 → 内置浏览器看 | 最简单、最安全 | **强烈建议先做这个**，一周能出 MVP |

**建议组合**：先做 C（查看器）+ 桌面端多平台；再补 A 的 iOS 备份路径（用户在电脑上备份一次，
把备份目录拖进 App 即可解析）；Android root 作为高级功能，不承诺。

移动端技术选型建议：

- **Flutter**：一套代码出 iOS/Android，内置 WebView 打开导出的 `chat.html` 成本很低
- 或者 **原生 + 本地 WebView**：如果只做查看器，其实一个带文件导入的 WebView 壳就够了
- 解密与解析继续用 **Python 引擎**：桌面端直接跑；移动端若要走 A 路线，需要把核心逻辑用 Dart 重写（AES/SQLCipher 在移动端有现成库）

## 5. 里程碑

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M0**（1–2 周） | 抽适配层：新增 `core/schema.py`、`platforms/base.py`、`platforms/wechat/` | 微信导出结果与现在**逐字节一致**（4603 条基线不回归）；`exporter.py` 未改 |
| **M1**（2–3 周） | QQ NT 适配器 | 能导出本人某个好友/群；1024 头剥离 + `kdf_iter=4000` + HMAC 实测确认；未知 protobuf 字段保留 hex |
| **M2**（3–4 周） | 飞书适配器（官方 API） | OAuth 授权 → 列会话 → 分页拉历史 → 附件下载 → 同一套 HTML/CSV；速率限制内不丢消息 |
| **M3**（2 周） | 链接卡片增强（抖音/B站/小红书） | 短链识别为卡片；离线模式只显示 URL，联网取标题为显式开关 |
| **M4**（4–6 周） | 移动端 MVP（形态 C，Flutter） | 手机上导入 PC 导出的 zip，能搜索、看图片、看视频 |
| **M5** | iOS 备份解析（形态 A 的 iOS 部分） | 用户提供 Finder 备份目录 → 直接得到微信记录，无需 PC 端解密 |
| **M6** | 分发：Windows 便携版（已有 skill 可做）、macOS 版、TestFlight | 零安装可运行；README 附安装说明 |

## 6. 风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| 平台改版导致取数失效 | 高 | 适配层隔离；自检里造数据不依赖真实样本；发版说明写清支持版本 |
| 账号被风控/封禁 | 高 | 只读内存、不注入；单次操作不做高频重试；README 明示风险 |
| 法律与合规 | 高 | 只处理本人数据；企业场景走官方 API；不提供"导出他人记录"的入口 |
| 商店审核被拒 | 中 | 桌面优先分发；移动端走 TestFlight/自签 |
| 移动端性能（大库、大图） | 中 | 分页加载、缩略图优先、生成静态页面而非实时渲染 |
| 钉钉/抖音承诺落空 | 中 | 一开始就把它们定义为"仅 API / 仅链接"，不承诺全量导出 |

   让现有微信链路先产出这个结构（纯重构，不改行为，用 4603 条基线做回归）。

   用 `kdf_iter=4000` + 两种 HMAC 算法各试一次 page1 校验——**先证明参数，再写代码**。
3. **移动端先做查看器**：一个 Flutter 壳 + 文件选择 + WebView，一周内能给自己用，
   然后再决定要不要碰备份解析。
